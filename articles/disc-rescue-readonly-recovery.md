家族を撮った DVD や、昔焼いた CD が、ある日パソコンで開けなくなる。ディスクは手元にまだ残っているのに、読めなくなったときに頼れる道具は意外と少ない。そこで「ディスクレスキュー」（英名 Disc Rescue）という Windows アプリを作りました。読めなくなった CD・DVD・ブルーレイから、読める部分を取り出すためのものです。

先に、やらないことを書いておきます。

- 元のディスクには書き込みも消去もしない（読み取り専用）
- 市販ディスクやテレビ録画のコピー防止を解除する機能は作らない
- 直らないディスクもある。「必ず戻る」とは言わない

この記事は宣伝というより、設計の話です。壊れかけた媒体から取り出すソフトは、うまく読めたふりをするのがいちばん危険で、そこから逆算して設計がほぼ決まりました。その中身を書きます。

構成は Rust のワークスペース（edition 2024、MSRV 1.85）で、画面は Tauri と React です。読み取りの核はすべて Rust 側にあります。

## 方針: 壊れた媒体の「嘘」を作らない

復旧ツールが最悪なのは、実際には読めていない範囲を「読めた」と言うことです。後から気づけないので、ユーザーは欠けた動画を「完全に取り出せた」と信じてしまいます。そこで次の不変条件を決め、コードの形もそこから決めました。

1. 元のデバイスには読み取りしかしない
2. 要求した長さちょうどで成功した範囲だけを「確定」とする
3. 不確かな状態を隠さず、区別して持ち続ける
4. 再開するときは、同じディスクだという内容の証拠を要求する
5. 再試行には必ず上限がある

以下、これが実装にどう出ているかを順に書きます。

## 1. 読み取り専用を型で守る

Windows では `IOCTL_SCSI_PASS_THROUGH_DIRECT` で SCSI のコマンドを直接ドライブに送れます。これは強力ですが、任意のコマンドを組み立てられるということでもあり、書き込みや消去のコマンドも原理的には送れてしまいます。

そこで、デバイスを扱う crate（`optirecover-device`）の外に出す API を、読み取りに限った trait だけにしました。

```rust
pub trait BlockDevice {
    fn geometry(&mut self) -> Result<Geometry, DeviceError>;

    fn read_blocks(
        &mut self,
        range: LbaRange,
        destination: &mut [u8],
    ) -> Result<ReadResult, DeviceError>;
}
```

生の CDB（コマンド記述子ブロック）を組み立てて送る処理は、この crate の中に閉じ込めています。取り込み側（imager）や CLI は、ブロックを読む関数しか呼べません。「書き込みコマンドを送らないよう気をつける」ではなく「送るための道具が外に存在しない」状態にするのが狙いです。`unsafe` と FFI も Windows 用モジュールの中だけに置き、操作ごとに `// SAFETY:` で根拠を書いています。ワークスペースの lint では `unwrap` と `expect` を禁止にし、メディアから来る値は敵対的な入力として扱って、オフセットや長さの計算は常に checked にしています。

## 2. セクタ 1 件ずつ記録しない: 範囲マップと 5 つの状態

DVD は数百万セクタあります。1 件ずつ状態を持つと、保存も更新も重くなります。そこで状態は「範囲」で持つことにしました。連続した同じ状態の範囲を 1 つにまとめ、読めた・読めなかったに応じて分割と結合をします。

状態は 5 つです。

```rust
pub enum RangeState {
    Unattempted = 0,
    ReadableConfirmed = 1,
    RetryableFailure = 2,
    ExhaustedFailure = 3,
    Skipped = 4,
}
```

「まだ読んでいない」「読めたと確定した」「失敗したがまだ試せる」「試す上限まで試して失敗した」「意図して飛ばした」を、最後まで区別して持ちます。読めなかった所を、ゼロで埋めて「回収済み」に見せることはしません。確定した範囲を後から降格させたり、黙って上書きしたりもしません。同じ場所に食い違うバイト列が来たら、重大な診断として扱います。

マップは画像ファイルのそばに SQLite で保存します（`<image>.opti-map.sqlite3`）。範囲の遷移のルール自体は SQLite に依存しない純粋なデータ構造に持たせ、SQLite は保存先として使う形にしました。イメージファイルだけでは、そのディスクをどこまで読めたかは証明できません。権威はマップのほうです。

## 3. 書く順序で、落ちても嘘をつかない

取り出し中にアプリが落ちたり、電源が切れたりしても、マップが実際より先に進んでいてはいけません。確定は「イメージに書く → ディスクへ同期する → マップを確定する」の順に固定しています。実際のコードから、確定を保存する部分を抜き出します。

```rust
fn flush_pending<I: ImageSink>(/* ... */) -> Result<(), AcquisitionError> {
    // ...
    image.sync_data().map_err(AcquisitionError::Image)?;
    store
        .save_map_with_anchors(&pending.map, &pending.anchors)
        .map_err(AcquisitionError::Store)?;
    // 証拠は状態の権威ではない。確認の保存が通ったあとに書く
    store
        .record_evidence(&pending.evidence)
        .map_err(AcquisitionError::Store)?;
    // ...
}
```

イメージの同期が済む前にマップが確定されることはありません。同期の直後、マップの保存の前に落ちた場合は、データは書けているのにマップが確定していない状態になります。再開すると、その範囲はもう一度読まれるだけです。無駄な読み直しは起きますが、読めていない範囲が確定済みになることはありません。設計文書にも「クラッシュは無害な再読を起こしうるが、偽の確認は起こさない」と書いています。

もう一つ、確定の条件を厳しくしています。SCSI のステータスが成功で、転送長が要求バイト数にちょうど一致し、その上で書き込みが成功したときだけ確定します。短い転送、残りバイト数があいまいな応答、CHECK CONDITION、タイムアウトは、一部が読めていても何も確定しません。必要なら範囲を細かく分けて読み直し、確定できる境界を見つけます。

## 4. 別のディスクにつないでしまわない: SHA-256 の内容アンカー

読み取りは数時間から数日かかることがあり、途中で止めて再開できるようにしています。ここで怖いのは、再開時に別のディスクを入れてしまうことです。同じ容量のディスクは珍しくなく、容量や構造が一致するだけで「同じディスクだ」と判断すると、別のディスクのデータが混ざったイメージができてしまいます。

そこで、確定した範囲の SHA-256 を「内容アンカー」としてマップと一緒に保存します。再開のときは、保存されたアンカーを実際のディスクと突き合わせ、3 個以上が一致しなければ再開を拒否します（`MIN_RESUME_ANCHORS = 3`）。形状の一致だけでは、結合を許可しません。間違ったディスクだけでなく、イメージ側が書き換えられていた場合も、この突き合わせで弾けます。

また、通常の再開では、試す上限まで失敗して `ExhaustedFailure` になった範囲を再試行しません。そこをもう一度試すのは、ユーザーが明示的に選ぶ別の操作です。放っておくと同じ傷んだ場所を何度も読み続けて、ディスクにもドライブにも負担をかけるからです。再試行には必ず上限があり、1 台の光学ドライブに対して並列に読むこともしません。

## 5. 段階的に読む: 速く → 詰める → 1 ブロックずつ

傷んだディスクを最初から小さい単位で読むと、時間がかかりすぎます。逆に大きい単位だけで読むと、1 か所の傷で周りの読めるデータまで失います。そこで、読み取りは 3 つの段階に分けています。

1. fast: 大きめのまとまり（既定で 32 ブロック）で、素早く読む。読めた範囲は確定する
2. trim: fast で失敗した範囲を、小さいまとまり（既定で 4 ブロック）で読み直す。失敗した範囲の端を削って、読める部分を増やす
3. single-block: それでも失敗した範囲を 1 ブロックずつ読む。ここまで試して読めない所だけが、最後に残る

各段階は、直前の段階がマップに残した結果を見て、次に読む範囲を決めます。読めなかった範囲が最終的に残っても、それは「失敗」としてマップに残り、レポートに出ます。ゼロのデータで埋めて、読めたことにはしません。

## 6. 音楽 CD は「読めた」を 1 回の成功で決めない

音楽 CD は、データ CD と違って、読めたかどうかを誤り検出の符号で確かめられません。ドライブが傷んだ所を補間して、それらしい音を返してくることもあります。1 回読めたことは、正しい音であることの証拠になりません。

そのため音楽 CD では、同じ場所を何度も読み直して比べます。C2 エラー情報が取れるドライブでは、C2 がすべてクリアな読み取りが 2 回一致したとき、取れないドライブでは 4 回一致したときに、はじめて「読めた」とします。一致しない所は候補として残し、確定扱いにはしません。読み直しの回数にも上限があります。

限界も、設計文書に書いてあります。補間を一貫して行い、しかも C2 を立てないドライブでは、この方法をすり抜けます。一致は安定して読めたことの証拠であって、正しい音であることの証拠ではありません。そのため、アプリの表示でも「元の音と同じ」とは言わないことにしています。確かめられなかった所は無音にして、どの曲のどのあたりかを一覧に出します。

保存したあとは、公開されているオンラインの記録（ディスクの目次にあたる数字の列を送って照合する）と突き合わせる機能もあります。送るのは目次の数字だけで、音や曲名は送りません。設定でいつでもやめられます。

## 実機で確かめたこと、まだのこと

ここは、確認できた範囲だけを書きます。

確かめたのは次の 2 つです。

- 傷のない音楽 CD を 1 枚（2026-10-19）、全部読んだところ、12 曲すべてがオンラインの記録と一致した。誤って確定した箇所は 0
- DVD 1 枚を全体まで読み終えた。誤って確定した箇所は 0

まだ確かめていないのは次のとおりです。

- アプリの画面からの CD の操作
- 傷のある音楽 CD
- オンラインの記録を使った「読めなかった所の修復」
- 取り消し・再開・アプリを開き直したあとの動き

単体テストでは、仮想ブロックデバイスに障害（媒体エラー、タイムアウト、短い転送、一度失敗してから成功する読み取りなど）を注入して、挙動を確かめています。壊れた ISO ファイルでは、ドライブが CHECK CONDITION を返す状況を再現できないので、障害の注入はデバイスの境界で行っています。ただし、それは実機の代わりにはなりません。実機での確認はまだ一部で、傷んだディスクでどれだけ戻るかはディスクの状態次第です。

## おわりに

作ってみて強く思ったのは、復旧ツールの価値の半分は「取り出せた量」ではなく「取り出せなかった所を正直に言えること」だということでした。その正直さを、気をつけるという心がけではなく、型・状態・書く順序・テストに埋め込む作業が、設計のほとんどでした。

ディスクによっては、ドライブに認識されないなど、専用の機材がある業者のほうが直せる場合もあります。このアプリは、そこまでは手を出しません。
